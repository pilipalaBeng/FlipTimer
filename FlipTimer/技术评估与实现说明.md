## 零、使用姿态（重要前提）

手机**横屏立在桌面上**（屏幕面向使用者，长边水平）。用户翻 180° = 在手机自身平面内转半圈，顶端朝下。

这不是"平放在桌上翻面"。两种姿态的重力分布完全不同：

| 姿态 | 重力落在哪 | z 分量 |
|---|---|---|
| 横屏立在桌上 | x 轴（x ≈ ±1） | **≈ 0** |
| 平放在桌面 | z 轴（z ≈ ±1） | ±1 |

这张表本身就说明了加速度计的局限：它只知道"哪边朝下"。手机平放在桌上、在桌面平面内转 180°，重力向量全程是 `(0, 0, 1)`，转前转后一模一样。真正的判据见第三章第 2 节——用陀螺仪 z 轴角速度，而不是任何一根重力轴。

## 三、技术决策

### 1. 先回答：有没有现成的"屏幕翻转"接口

**没有。** 小程序能拿到的"屏幕方向"全部只有横/竖二分，没有任何一个能返回"倒置"状态。

| 接口 | 返回 | 能判 180°？ |
|---|---|---|
| `wx.getSystemSetting().deviceOrientation` | `portrait` / `landscape` | ❌ 只有两个值 |
| `wx.onResize` / `onWindowResize` | 视口宽高 | ❌ 只能算横竖 |
| `pageOrientation: "auto"` | 页面自动转向 | ❌ iOS 页面不支持 upsideDown |
| `wx.onDeviceOrientationChange` | `landscape` / `landscapeReverse` | ⚠️ 仅小游戏可用，且只区分左右横屏，需 `game.json` 配 `deviceOrientation: landscape`；小程序页面侧无此接口 |
| `wx.onDeviceMotionChange` | alpha / beta / gamma（弧度） | ✅ 需自算 |
| `wx.onAccelerometerChange` | x / y / z（g） | ✅ 需自算 |

根因：屏幕旋转是操作系统层的私有服务，小程序只能拿到它算好的降维结果（横/竖），拿不到原始姿态。**系统能"自己转"不等于小程序能"问到转没转"。**

所以判断必须自己做。

### 2. 为什么加速度计不行（这一版推倒重来的原因）

最早用的是 `wx.onAccelerometerChange`，判据是单位重力向量的点积：翻 180° 后重力方向反了，点积 ≈ −1。

**这个判据在"立着翻面"时成立，在真实使用姿势下彻底失效。**

真实姿势是手机**平放在桌上**，在桌面平面内转 180°。这时设备的重力向量始终是 `(0, 0, 1)` —— 转前转后**完全一样**，加速度计读不出任何差别。它只知道"哪边朝下"，不知道"屏幕朝哪边"。

真机表现就是：翻十次中一次（靠转动时手抖出来的那点倾斜），而且只在一个方向像是有效。不是阈值没调准，是传感器选错了。

能测这个动作的是**陀螺仪的 z 轴**：绕屏幕法线旋转时，z 轴角速度会给出清晰的正负读数，与手机是平放还是立着无关。

顺带说明为什么不用 `wx.onDeviceOrientationChange`：它只在小游戏里可用，且只区分左右横屏；小程序页面侧根本没有这个接口。

### 3. 判据：z 轴角速度积分

累加 `z × dt`，绝对值过 150° 就确认一次翻转。四个常量各管一件事，缺一个都会坏：

| 常量 | 值 | 作用 |
|---|---|---|
| `OMEGA_DEAD` | 0.35 rad/s | 死区。静止零偏远低于它，正常转动至少高一个量级。没有死区，零偏会慢慢积分成假翻转 |
| `TURN_RAD` | 150° | 剩下 30° 交给惯性。要求转满 180° 会让人觉得"我明明翻了它没反应" |
| `SPIN_HOLD_MS` | 8000ms | 静止这么久才丢弃累积量，好让"转 90° 停一下再转 90°"能累积成一次 |
| `MAX_DT_MS` | 120ms | 单帧积分上限。小程序被挂起再回来，两帧间隔可能是几十秒，不钳住会把一次恢复当成一次高速旋转 |

**`dt` 必须除以 1000 换成秒。** 角速度单位是 rad/s，直接拿毫秒相乘会把结果放大一千倍，屏幕上一丝抖动都够触发一次翻转。这个 bug 写过一次，仿真当场 10 条用例全红。

**取 `Math.abs(this.spin)`** —— 正转和反转走同一条式子，天然对称，不存在"只认一个方向"。

### 4. 一次翻转只兑现一次

转到 150° 就确认，但用户的手会继续把剩下 30° 转完。这部分不能留到下一次：留了之后，反方向翻转就得多转十几度才触发，来回几次明显变钝。

所以确认后 `spin = 0` 并置 `spinDone = true`，之后的旋转一律不计入；直到角速度掉进死区（手停下了）才复位。再加一条 1.2 秒的时间兜底——手一直在轻微动时角速度可能始终在死区上方，只靠"停下来"复位会把后面所有翻转都吞掉。

### 5. 双向对称；姿态和动作分两条路走

姿态翻到另一面和翻回原位，是两次对称的合法翻转，物理上无法区分"主动"和"顺手翻回"。旧版本用 `armed` 记账：只有"没被用掉"的翻转才允许启动。它解决的是真问题（关掉提醒后把手机翻回原位，不该又开起来），但代价是**只有一半的翻转算数**——任何一次未被消耗的翻转都会吃掉武装，用户感受到的就是"有时候翻一下没反应，得再翻一次"。

后来换成 3 秒时间冷却，更糟：冷却叠在 1.5 秒关闭反馈期后面，反馈期结束、屏幕已经回到待机，翻一下还是被剩下的 1.5 秒挡住。**这就是"翻一下没反应"的主因，已删除。**

现在只剩两层：

- **判据里不出现"上一次翻转是否已用过"这种单向状态。**
- **防误启动只靠 `showClosed` 的 1.5 秒反馈期**：反馈期内 `state === 'closed'`，翻转本来就进不来；反馈期一过就是待机，翻一下必须立刻启动。

#### 动作走队列，不走回调（这一条是血换来的）

真机上出现过一组读代码解释不通的现象：**界面转到了 B 面，计时却没起来。** 原因在 `_commitTurn()` 原来的写法：

```js
this._setPose(!this.upsideDown)  // 渲染：要碰 setData
this.onFlip()                    // 动作：紧接在同一行之后
```

渲染那步一旦出岔子，后面的动作就一起被带走了；而传感器回调栈里的异常**只进 console，页面上零提示**。

现在 `_commitTurn()` 里顺序固定，不能换：

```js
this.turns++
this.pending++                    // 记账：纯数值，不可能失败
this._setPose(!this.upsideDown)   // 渲染：失败了也不影响上面那笔账
```

页面在自己的滴答里取走执行：

```js
const turns = this.flipDetector.takeTurns()
for (let i = 0; i < turns; i++) this.consumeTurn()
```

代价是响应最多晚一拍（200ms），换来的是**事件不可能丢**：`pending` 是计数，不会被任何渲染问题吃掉，异常也发生在页面栈里、带得出来。

另外，`_commitTurn()` 被 `lockUntil` 挡下时**不再清零 `spin`**——清零再返回等于把用户已经转过的 150° 直接扔掉，这一下就白翻了。

页面侧的裁决只剩三种走向：

```js
if (state === 'alert') return this.closeAlert()   // 提醒态一翻就关
if (state !== 'idle') return this.noteFlip(...)   // 计时中 / 反馈期不响应
this.beginRound()                                 // 待机就启动
```

### 6. 降级路径：加速度计点积

陀螺仪不是每台机器都起得来（老基础库、系统权限被收走）。`_startGyro()` 失败时退回加速度计，判据是原来那套：

| 点积 | 含义 | 处理 |
|---|---|---|
| ≈ +1 | 同向，没翻 | 忽略 |
| ≈ 0 | 换了摆放方式（立 ↔ 平） | 不动作，稍后挪基准 |
| ≈ −1 | 方向反了，正好 180° | 触发 |

阈值 `GRAV_DOT = -0.7`（夹角约 134°），姿态要连续保持 260ms 才采纳（`GRAV_SETTLE_MS`），中性区连续停 1200ms 才挪基准（`GRAV_REBASE_MS`）——不挪的话基准会永远卡在旧姿态，之后所有动作失灵。

两条路不并行：陀螺仪成功就不启加速度计，姿态只由其中一条维护。否则加速度计那套 rebase 会把陀螺仪维护的姿态强行打回正立。

### 6. 内容跟随旋转

`flip.js` 除了上报动作，还实时上报姿态（`onPose`）。页面给整个内容层加 `rotate(180deg)`，620ms 缓动。
手机倒过来，字也跟着倒过来，相对人眼仍正立。

注意：界面姿态**始终跟随物理姿态**，与是否触发动作无关——翻回时界面要转回去，但不触发动作。这一点最初写错过，被仿真抓出来了。

### 7. 显示层：中间区永远是当前时钟

这一版把产品定位摆正了：**它首先是一台时钟，计时只是附带功能**。

中间区任何时候都显示当前时刻，不显示倒计时：

| 状态 | 中间显示 | 为什么 |
|---|---|---|
| 待机 | `HH:mm` | 它就是一台钟 |
| 计时中 | `HH:mm` | 同上，计时在后台按时间戳走 |
| 最后一分钟（剩余 ≤60s） | `HH:mm:ss` | 秒出现，作为"快到点"的无声提示 |
| 提醒 | `HH:mm` | 还是钟。提醒只由边缘的光表达 |

好处是用户不需要理解"我现在看的是剩余还是时刻"——钟永远是钟。计时状态只由底部一行小字和到点提醒体现。

`HH:mm:ss` 比 `HH:mm` 多两个冒号段（5 字符 → 8 字符），字号必须同步缩小（`42vh → 30vh`）并加 `font-size` 过渡，否则横向溢出。缩完两种格式占屏宽约 64% / 71%，切换时不跳。

取时统一走 `renderClock()`，内部永远 `new Date()` 现取，不缓存、不推算。

「带秒」是**双条件**：剩余 ≤60 秒 **且状态是 `running`**，两个条件都写在 `renderClock()` 里面，不靠调用方自觉。到点进入提醒的同一刻秒就收掉——那串秒是"快到点了"的提示，到点即失效，留着只会让人以为还在倒计时。守卫放在取时入口，任何地方误传 `true` 都拦得住。（C-3.4）

计时层与显示无关：剩余时间永远现算 `targetTs - Date.now()`，200ms 定时器只负责重绘。切后台、掉帧、锁屏都不会累积误差，回到前台立刻正确。

### 8. 冷启动恢复：只存一个时间戳

小程序被系统杀掉后重进，`onLoad` 会重新执行，进行中的计时本来会丢。存的东西只有一个数：**本轮目标时间戳**（`flip_timer_round_target`）。

因为剩余时间本来就是现算的，存了目标时间戳就等于存了整个计时状态，不需要存剩余秒数、进度、状态名。

恢复规则：

| 存储内容 | 重进后的状态 | 依据 |
|---|---|---|
| 无 | 待机 | 没有进行中的轮次 |
| 有，且 `targetTs > now` | 计时中，剩余按时间戳现算 | 本轮还没到点 |
| 有，且 `targetTs ≤ now` | 提醒态，重新亮呼吸光 | 到点了但**从未被关闭**，提醒理应还在 |

写入 / 清除的时机：

- `beginRound()` 写入
- `closeAlert()` **即刻**清除（不等 1.5 秒反馈期），否则反馈期内被杀、重进会又弹一次提醒
- `toIdle()` 再清一次做兜底

和前端状态机一致：恢复后仍然**不自动开始下一轮**，提醒态也必须由用户翻转/点击关闭。

`test/simulate.js` 后三条专门守这个行为（中途被杀恢复剩余、到点未关闭仍提醒、关闭后重进待机）。

### 附：画面跟手、动作却不发生 —— 先量，别再猜

有一组现象读代码解释不通：待机时翻转画面跟着转（说明姿态在变），但翻转不启动计时（说明动作没派发）。这两件事如果同时成立，只剩一种解释——**那个"转"不是本页转的**，是 WeChat 横屏自己在跟设备。

绕屏幕法线的 180° 旋转，系统层面会不会替你把画面转过来，取决于 `pageOrientation: landscape` 在当前机型上的实现：跟，则本页再转 180° 就是双重旋转，画面永远停在原来那一侧；不跟，则必须由本页补这个 180°。而**这两件事在代码里没有任何 API 可以区分**，只能实测。

所以加了一块自检读数（`utils/debug.js`，页面左下角）：

```
S gyro n412 w0.82 176° B t3   传感器路径 / 帧数 / 实时 z 角速度 / 累计角度 / 姿态 / 已确认翻转次数
ST idle p0 blk st:running     状态机 / 待消费队列长度 / 最近一次翻转的处理结果
ROT ON                        点一下关掉本页的 180° 补偿
```

判读办法只有一句：**把 ROT 关掉，再翻一次。** 画面还正着 → 系统在转，本层多余，删掉；画面倒过来 → 本层必需，问题在传感器。

动作走队列之后，`t` 和 `p` 把"卡在哪一步"直接分开了：

| 面板上看到的 | 说明 |
|---|---|
| `t` 翻的时候不涨 | 传感器没认出这次旋转（死区 / 阈值 / 根本没收帧，看 `n`） |
| `t` 涨了、状态没变 | 事件取到了但被挡下，`blk st:running` 之类直接指出是谁挡的 |
| `p` 长期大于 0 | 滴答没在跑，事件堆着没人取 |
| `blk` 位置出现 `err ...` | 动作执行时抛异常，消息就在后面 |

这块是临时仪表，收敛后连同 C-6.4 的临时放宽一起删。

## 五、必须真机验证的 6 件事

仿真是纯逻辑验证，**传感器手感和横屏行为必须上真机**。

| # | 验证项 | 怎么看 | 改哪里 |
|---|---|---|---|
| 1 | 竖排方向锁定下 `landscape` 是否强制横屏 | 开锁定后进小程序 | 若不行只能引导用户关锁定 |
| 2 | 初始摆放方向是否顺 | `landscape` 固定单向，反着放会看到倒的内容 | 反过来放即可 |
| 3 | 翻转灵敏度 | 横屏立着翻 180° 是否一次成功；拿起手机是否误触 | `SETTLE_MS`（当前 260ms） |
| 4 | 内容旋转是否跟手 | 翻转时字是否稳、有无明显延迟 | `.flipper` 的 transition（当前 620ms） |
| 5 | 呼吸光被手机壳遮挡程度 | 装壳后看边缘 | `.glow` 内缩值 |
| 6 | 低电量模式下常亮是否失效 | iOS 开低电量模式 | 失效只能在界面提示 |

## 七、已确认的取舍

### 中间区显示：永远是当前时钟（已定）

策划案 v0.2 原本是"中间显示倒计时，最后一分钟显示纯秒"。**已推翻，改成：中间永远是当前时间，最后一分钟才带上秒。**

理由是产品定位：这是一台放在桌上的时钟，计时是它附带的功能。让倒计时占据主视觉，等于把它做成了倒计时器，本末倒置。

代价是用户看不到"还剩多少"，只能看右下角的提醒时间。这个代价由产品接受。

### 操作入口：右上角悬浮钮（已定）

底部横排按钮已经删掉。现在所有入口收在**微信胶囊正下方**的一根细棍里：点开长出纵向菜单（时长 / 光色 / 开始，提醒态是关闭），3 秒没操作自己缩回。

两个关键约束：

- **位置由胶囊矩形算**（`wx.getMenuButtonBoundingClientRect()`），不写死 `vh`。异形屏、分屏下胶囊会漂，写死迟早撞进去。
- **必须放在旋转层之外**。胶囊是原生层，页面翻转 180° 时它不转；钮要是跟着内容转，就会跑到对角去——这正是上一版「按钮只能放底部中间」的真实原因。钮只跟屏幕不跟内容，翻不翻都贴在胶囊下面。

### 提醒光配色：JS 拼完整 rgba 串，不给取色器（已定，2026-10-20 真机返工）

颜色只给三档（绿 / 红 / 蓝），强度只给三档（淡 / 标准 / 浓，倍率 0.72 / 1 / 1.3）。

**为什么不暴露原始 alpha**：`0.38` 这种数值对用户没有意义；而且真放开就是能调到把中间的时钟冲掉——那是一台时钟，光再好看也不能吃掉时间。

**为什么是 JS 拼串，不是 CSS 变量**：光的形态是 3 层 `box-shadow` + 4 条 `linear-gradient`，一共 7 处色值，三色 × 三档手写就是 63 个色值。第一版想用 CSS 变量解决，写成 `rgba(var(--gc), var(--a1))` —— 在 Chrome 里完美，在真机上一片黑。

原因是 **WXSS 编译期会逐个校验 `rgba()` 的参数**，撞上 `var()` 这种非数值就把整条声明丢掉。不报错、控制台干净、代码看着完全正确。`preview.html` 至今还能正常发光，因为那是浏览器。

所以改成 `prefs.glowStyles(color, level)` 直接返回成品字符串：

```
near: "box-shadow: inset 0 0 2vh 0 rgba(94, 214, 160, 0.38), …"
far:  "background-image: linear-gradient(to bottom, rgba(94, 214, 160, 0.14), rgba(94, 214, 160, 0)), …"
pre:  "box-shadow: inset 0 0 2.5vh 0 rgba(…), …"
```

绑到 `style` 属性上——运行时字符串，WebView 直接解析，不过编译期校验。`styles/glow.wxss` 里只剩几何和动画。

**红线：任何地方都不许再出现 `rgba(var(--x))`。** C-7.15 和宪法自检都盯着这一条。

**兜底必须回落到显式默认值**，不能用"列表第一项"。强度列表第一项是「淡」，用 `list[0]` 兜底会让"存储被写坏"和"首次进入"落到不同档位——这个坑是仿真测出来的。

**面板必须有实时预览条**。待机态屏幕本来不发光，用户在设置里改完看不见任何变化，等于盲选。预览条用同一份样式串和同一段 `breathe` 动画，不做第二套实现。

### 传感器启动不套隐私授权（已定 2026-10-20，踩过）

`flipDetector.start()` 在 `onShow` 里直接调 `wx.startAccelerometer`，**不经过 `wx.requirePrivacyAuthorize`**。

加速度计 / 陀螺仪不在微信隐私接口名单里，本来就不需要授权。上一版套了一层，结果隐私保护指引没生效（本项目长期审核中）时它会直接 `fail`，把传感器一起拖死——真机现象就是"手机翻过来了，界面纹丝不动"，检测层完全正常，只是压根没启动。启动失败只走 C-4.6 的静默降级。

### 提醒态长什么样、怎么关

到点后进入 `alert`，屏幕只做三件事：

| 元素 | 表现 |
|---|---|
| 屏幕四周 | 从**物理边缘**向内的渗透光（绿/红/蓝三色可选），`opacity 0.3 ↔ 1` 呼吸，5 秒一个来回，无限循环 |
| 中间 | 不变，还是当前时间 `HH:mm`，并且**继续走时** |
| 右下角 | 提醒时间擦掉，不残留 |
| 底部 | 一行小字「翻转或点击关闭」 |

不出声、不震动，这是"静音办公"的前提。

### 渗透光：为什么单靠 box-shadow 做不出"带宽"

第一版是内缩一圈 + 单层 `inset 0 0 6vh 0.6vh`。那是**一条硬边亮带**：`spread 0.6vh` 先扩出一段实心区再模糊，亮带内沿和黑屏之间是断崖，看起来像在屏幕四周贴了一圈荧光胶带。

第二版改成五层同色阴影叠加，模糊半径逐层放大、alpha 逐层减半。形态对了，但用户反馈**"带不大、不明显"**。截图量化后找到真因：

> `box-shadow` 的高斯衰减在 30vh 之外已经掉到 alpha < 0.05，肉眼看不见。**半径再拉长，也只是"更长的看不见"。**

试过纯阴影六层（中远场 alpha 抬到 0.10 / 0.075 / 0.055），效果仍然不够，而且四角因为两个方向叠加而发亮、每条边的中点发暗，形成 X 形不均匀。**这条路走不通，不是参数没调好。**

现在的实现分两段职责：

| 段 | 手段 | 干什么 |
|---|---|---|
| 近场 | `.glow` 的 3 层 `box-shadow` | 只管贴边最亮那一圈。3 层足够——都在同一小段距离里衰减，堆多了是重复描同一段边 |
| 远场 | `.glow-far` 的四条渐变带 | 把 Alpha 从中段手动抬起来，做出真正的带宽 |

远场的关键是**用 `background-size` 控制带宽，而不是用 stop**：

```css
.glow-far {
  background-image:
    linear-gradient(to bottom, rgba(94,214,160,.14), rgba(94,214,160,0)),
    linear-gradient(to top,    rgba(94,214,160,.14), rgba(94,214,160,0)),
    linear-gradient(to right,  rgba(94,214,160,.14), rgba(94,214,160,0)),
    linear-gradient(to left,   rgba(94,214,160,.14), rgba(94,214,160,0));
  background-size: 100% 24%, 100% 24%, 24% 100%, 24% 100%;
  background-position: top left, bottom left, top left, top right;
  background-repeat: no-repeat;
}
```

每条渐变在自己的 24% 条带里从 0.14 完整走完到 0。**如果在渐变里写中途 stop**（比如 `rgba(...,.14) 0%, rgba(...,0) 34%`），衰减会在 34% 处突然归零，与相邻层之间留下一条**屏幕上看得见的直边**。带宽只由 `background-size` 表达，这条规则写进了 C-7.5 并有变异用例守着。

另外三条：

- **四边统一 24%，不为"物理等深"改成 vw/vh 混用**。横屏长边是短边的 2.17 倍，同一个百分比换算成像素后左右自然更长，视觉带宽才均衡。反过来追求物理等深，左右只剩 13% 的视觉带宽，看着像只有上下在发光。**这里观感优先。**
- **中间必须纯黑**。四条带在 24% 处归零，中心不叠任何颜色。不用全屏单层渐变，那会把时钟数字的对比度一起吃掉。
- **谷底 `opacity: 0.3`**，不更低。落到 0.2 时边缘 alpha 只剩 0.076，一个 5 秒周期里大半时间"看起来没在提醒"。
- **`.glow-on` 必须有静态 `opacity: 1`，不能只靠动画**。呼吸是 `animation` 改 `opacity`，而 `.glow` 的基准值是 `0`——动画一旦不跑（iOS「减弱动态效果」、低电量模式、WebView 回收合成层），opacity 就停在 0，屏幕**一片黑**，现象和 1.13 那个 WXSS 编译坑完全一样，却更难查。加了静态 1 之后：动画正常时照旧呼吸，动画被掐掉时静态全亮。**"光在"这件事不能依赖动画。**

光效整块抽到 `styles/glow.wxss`，由 `index.wxss` 用 `@import` 引入。它是一块独立的视觉单元，也顺便让页面样式文件回到 400 行以内——**上限没有因为塞不下而放松**。

手机上装壳压边的情况确实存在，但那是"边缘一部分被挡"，视觉上仍然是连续的光，比为了躲壳而内缩一圈好看得多。

**关闭有四条路，优先级从直觉到兜底**：

1. **翻转 180°** —— 一次就关，两个方向都算（见第 5 节）
2. **点屏幕任意位置** —— 整屏 `bindtap`，不需要瞄准
3. **长按中央区** —— 和计时中取消共用一套长按入口
4. **右上角细棍 → 关闭** —— 传感器彻底不可用（启动失败、权限被系统收走）时的兜底

关掉后进 `closed`：中间只回一句「好了」，底部留空不重复，1.5 秒后回待机，**不自动开始下一轮**（C-2.3）。

### 提醒态不设超时：一直亮到用户动手（已定）

用户一直不关提醒，呼吸光就**一直亮着**，不加自动回待机。理由是"提醒未被确认关闭"就该持续提醒，这是产品的核心语义。

这条要在两层同时成立，缺一层就会破：

- **状态机层**：`alert` 的出口只有用户动作（翻转 / 整屏点击 / 长按 / 悬浮钮关闭）。**禁止**任何 `setTimeout`、计数到点、"重进页面自愈"式的自动结束。仿真有一条用例专门推两小时，确认它还在 `alert`。
- **样式层**：光不能只靠动画存在（`styles/glow.wxss` 里的静态 `opacity: 1`，见上一节）。否则系统一掐动画，"一直提醒"就变成了"一直黑着"。

### 计时中怎么中止：长按中央区取消（已定）

第一版的 `running` 态是个死胡同：只能等到点、提醒、关闭，中间没有任何出口。番茄钟被电话打断、临时要出门，用户只能眼睁睁看着它继续跑。

补的入口是**长按中央区**：

- 不占用任何视觉空间，底部小字仍然是干净的「计时中」。
- 不走翻转。计时态翻转不响应是硬规则（C-2.4），取消和启动不能共用同一个手势，否则"翻一下"的语义会分裂成两种，反而更乱。
- 不点按钮。全黑界面上挂一个"取消"按钮，是给每轮计时都留一个误触陷阱，也会毁掉静默感。
- 长按 350ms 才会触发（系统 `longpress`），手指划过、擦屏幕都不会误伤。误触了也不怕：取消后不自动开始下一轮，翻一下就能重新起。

取消后中间显示「算了」，1.5 秒回待机，和关闭提醒共用同一套反馈（`showClosed`），只是文案不同。

### 防烧屏：不做像素偏移（已定）

策划案 5.1 要求"数字做 1~2 像素级微移，降低 OLED 烧屏风险"，**已移除**。

原因很简单：这个手段在量级上就不成立。9vh 的大字在真机上接近 100px 高，挪 1px 只改变约百分之一的行；四档轮换的最大位移 2px，覆盖面积不到 2%。而 OLED 的老化差异取决于**单个像素的累计点亮时长**——这种量级的位移不会改变任何一个像素的累计时长分布。它安慰的是心理，不是屏幕。

现实评估：

| 情况 | 后果 | 要不要防 |
|---|---|---|
| 正常使用（每轮 25~45 分钟，一天几轮） | 无 | 不需要 |
| 忘记关、亮一整夜 | 暂时残影，切画后十几分钟到几小时自行消退 | 不需要 |
| 连续几周同一画面常亮 | 才可能形成永久烧屏 | 但这不是本产品的使用方式 |

真要防，有效手段只有两个：整体降亮度，或让内容做几十像素级的大幅位移——两者都会毁掉"全黑极简时钟"的观感，不做。

代码里 `startDrift` / `stopDrift` / `DRIFT_MS` / `driftIndex` / `drift-0~3` 已全部删除，`.js` `.wxml` `.wxss` 无残留。
